# 技术方案

产品决策见 [product-decisions.md](product-decisions.md)，支付依据见 [payment-research.md](payment-research.md)。店铺网站的部署方案见文末。

## 技术栈

和 hive 保持一致，方便复用代码和经验：

- pnpm monorepo，TypeScript，ESM
- 服务端：Hono，Drizzle ORM，Postgres。本地开发和测试用 PGlite，不需要 Docker
- 前端：React 加 Vite
- MCP：`@modelcontextprotocol/sdk`
- 支付：`alipay-sdk`，外加一个本地用的假支付实现
- 商家 agent：Claude API，包括视觉识别。具体模型在实现时确认
- 校验：zod，前后端和 MCP 共用同一套 schema


## 数据模型

所有店铺共用一套固定的表，用 `shop_id` 区分。agent 只写数据行，不改表结构。

| 表 | 关键字段 | 说明 |
|---|---|---|
| `shops` | slug、名称、行业、联系方式、地址、营业时间、取消规则、收款配置 | `slug` 用在分享链接 `/s/:slug` 里 |
| `shop_pages` | `config`（JSON）、`theme`（JSON）、版本号 | 页面结构：启用了哪些模块、顺序、各模块参数。每次改动存一个新版本，可以撤销 |
| `products` | 名称、描述、图片、价格、`fulfillment`、时长（预约类）、`order_options`（JSON）、`info`（JSON）、是否为示例内容 | 下单选项和展示信息用 JSON；规格变体单独建表 |
| `product_variants` | 规格组合、价格、库存（零售类）、容量（预约类） | 没有规格的商品也有一个默认变体，下单时统一引用变体 |
| `availability_rules` | 每周哪几天、几点到几点、同时可服务人数 | 可预约时段**按规则实时计算**，不预先生成。已预约的订单占掉容量 |
| `orders` | 状态、来源（网页或 agent）、顾客联系方式快照、地址、预约时间、金额、快递单号 | 状态机在 `core` 里 |
| `order_items` | 变体、数量、单价、下单选项的值 | |
| `customers` | 按手机号区分，每家店独立 | 每笔订单自动生成或更新；记录到店次数、累计消费 |
| `payments`、`refunds` | 支付宝交易号、状态 | |
| `agent_threads`、`agent_messages` | 商家和 agent 的对话记录 | |

## 页面配置示例

```json
{
  "theme": { "primary": "#e86a92", "font": "rounded" },
  "sections": [
    { "type": "banner", "id": "b1", "props": { "title": "周末法式 8 折", "image": "..." } },
    { "type": "booking", "id": "k1", "props": { "productIds": "all" } },
    { "type": "gallery", "id": "g1", "props": { "images": ["..."] } },
    { "type": "custom_html", "id": "c1", "props": { "html": "..." } },
    { "type": "contact", "id": "ct", "props": {} }
  ]
}
```

每种模块在 `core` 里有一份定义，包括参数 schema、能否用于 agent、对应的 MCP 读写能力。网页渲染器、商家 agent 的工具、MCP 都从这份定义出发。

### 模块怎么扩展

配置驱动的店铺靠下面几层来满足不同商家的需求，从上到下越来越少用到：

1. **参数和主题**：每个模块有多种参数和布局变体，主题提供颜色、字体、圆角等设计变量。agent 主要在这一层组合
2. **数据字段**：规格变体、下单选项、展示信息（决策 4b），不改表结构就能覆盖不同行业
3. **行业模板**：每个行业一套预设，包括默认模块、示例内容、主题
4. **自定义 HTML 区块**：agent 可以写 HTML 和 CSS，处理个别需求；不允许脚本，或者放在沙箱 iframe 里
5. **平台新增模块**：agent 做不到的请求记录成“未满足的需求”，多个商家提出的同类需求由我们做成正式模块，所有店都能用

模块的参数 schema 带版本号。模块升级时，提供一个迁移函数，把旧配置迁移到新版本，保证老店铺不会坏。

## API

**店铺公开接口**（网页和 MCP 共用）：

- `GET /api/s/:slug`：店铺信息、页面配置、当前活动
- `GET /api/s/:slug/products`、`GET /api/s/:slug/products/:id`
- `GET /api/s/:slug/availability?variant=&date=`：可预约时段或库存
- `POST /api/s/:slug/orders`：下单，返回订单号、订单凭证和收银台链接
- `GET /api/orders/:id?token=`、`POST /api/orders/:id/cancel?token=`

**商家接口**（需要登录）：店铺设置、页面配置、商品增删改、订单处理（发货、同意取消）、顾客列表和导出、agent 对话。

## MCP 和 Skill

MCP 工具（服务端 `/mcp`，以及本地 `openshop mcp` 的 stdio 版本）：

| 工具 | 作用 |
|---|---|
| `shop_open` | 用分享链接或 slug 打开一家店，返回店铺信息和商品概览 |
| `shop_search_products` / `shop_get_product` | 查商品；返回变体、下单选项、展示信息，并标明哪些需要问用户 |
| `shop_get_availability` | 查可预约时段或库存 |
| `shop_create_order` | 下单，预约类必须带时段，零售类必须带地址；返回收银台链接 |
| `shop_get_order` / `shop_cancel_order` | 查订单、取消订单 |
| `profile_get` / `profile_save` | 只在本地版本里有，读写 `~/.openshop/profile.json` |

Skill 负责教 agent 的流程：问清楚该问的 → 展示订单摘要并确认 → 下单 → 把收银台链接交给支付宝官方的支付 Skill（`alipay-payment-skill`）→ 查询订单直到确认。

**决定（2026-10-21）：** 付款环节交给支付宝官方的支付 Skill 处理，由它调用 `alipay-bot`，并负责安装 `alipay-bot` 和开通钱包授权。我们的 Skill 不直接调用 `alipay-bot` 的命令，这样支付宝更新命令时，我们不需要跟着改。

## 支付

`PaymentProvider` 接口，两种实现：

- `FakePaymentProvider`：本地开发和测试用，给一个假收银台页面，点一下就算付款成功。可以参考 hive 的写法
- `AlipayPagePayProvider`：调用 `alipay.trade.page.pay` 生成收银台链接，用 `alipay.trade.query` 主动查询结果，退款用 `alipay.trade.refund`。每家店读取自己的收款配置；黑客松阶段只有一家店配置了真实凭证

本地没有公网，收不到支付宝的异步通知，所以付款结果改为主动查询：消费者回到对话时查一次，服务端也定时轮询未付款的订单。

## 商家 agent

服务端调用 Claude API，给模型一组工具，所有工具都只改数据：

- `update_shop`、`update_theme`、`add_section` / `update_section` / `move_section` / `remove_section`
- `upsert_product`、`delete_product`、`set_availability`
- `import_from_image`：识别图片，返回**待确认的商品列表**，不直接写入。商家确认后再批量写入
- `list_orders`、`get_customer`：回答经营问题

每次修改都会生成一个新的页面版本，网页预览实时刷新，可以撤销。

## 技术风险

- **`alipay-bot` 的 agent 支付链路能否用沙箱测试**：文档没有说明。如果不能，M5 必须用真实账号小额测试
- **拍照识别的准确率**：先用打印的价目表测，手写的作为加分项
- **可预约时段的并发**：两个人同时抢同一个时段，下单时要加锁，或者在事务里检查容量

## 店铺网站的部署方案

### 核心：发布不需要构建

每家店不是一份独立的代码，而是一份页面配置加业务数据（决策 4）。所以"部署一家店"不是构建和上传代码，而是**把待发布的修改应用到线上数据**。哪些修改要先预览、哪些立即生效，见下面"预览与发布"一节。

所有店铺由**同一个渲染服务**提供：请求进来后，按域名或路径找到对应的店，读取已发布的配置，渲染成页面。新开一家店不需要新部署任何东西。

### 预览与发布

**先区分两类修改：**

| 类型 | 例子 | 生效方式 | 理由 |
|---|---|---|---|
| **内容修改** | 页面结构、主题、横幅、商品名称、价格、描述、图片、规格 | 先进入**待发布修改**，预览确认后才上线 | 顾客看得见，改错了有损失（比如识图把 168 识别成 16.8） |
| **经营操作** | 改库存、关闭某个时段（请假）、标记发货、处理退款 | **立即生效** | 本来就是实时的；如果库存也要"发布"，就会超卖 |

Shopify 的做法是商品修改立即生效，只有主题可以草稿预览。我们的修改大多由 agent 发起，所以把商品内容也纳入预览，更稳妥。

**待发布修改（changeset）的机制：**

- agent 或商家的每次内容修改，都记成一条操作，例如"新增商品 酸菜鱼 ¥42""主色改为 #e86a92"，存进这家店当前的待发布修改里
- 预览时，渲染服务读取**线上数据加上待发布修改**，渲染出"发布后的样子"
- 线上网站、MCP、消费者的 agent，只读线上数据，看不到未发布的内容
- 点"发布"时，在一个数据库事务里把所有操作应用到线上数据，记录一个发布版本，然后清掉缓存
- 单条修改可以撤销，也可以整体放弃；已发布的版本可以回滚

**商家在工作台里的预览体验：**

1. **实时预览**：对话框旁边是一个预览窗口。agent 每改一处，预览马上刷新（服务端推送事件通知前端），**改动的区块会高亮**
2. **修改清单**：agent 每轮回复都附一张清单，比如"改了 3 处：主色 粉→红；新增横幅'周末 8 折'；酸菜鱼 ¥38→¥42"。每一条都能单独撤销
3. **切换手机和电脑视图**：大部分顾客会在手机上打开
4. **手机扫码预览**：生成一个带签名、限时有效的预览链接和二维码。商家可以用自己的手机看真实效果，也可以发给合伙人看
5. **发布确认**：点"发布"时列出自上次发布以来的全部修改，确认后上线

**数据模型的调整：**

- 新增 `changesets` 表（每家店最多一个进行中的）和 `changeset_ops` 表（每一条操作）
- 新增 `publishes` 表，记录每次发布的内容，用于回滚
- `shop_pages` 只存线上版本，不再区分草稿和已发布

### 商家管理后台

管理后台做在我们的网站上（工作台的一部分），和 agent 对话并列。**两者操作的是同一份数据**，商家想自己动手就用后台，想说一句话就找 agent。

| 页面 | 功能 | 生效方式 |
|---|---|---|
| 商品 | 列表、新增、编辑、规格、下单选项、上下架 | 内容修改，先预览 |
| **库存与时段** | 零售：按规格改库存，设置低库存提醒。预约：设置每周营业时段和可服务人数；临时关闭某天或某个时段 | **立即生效** |
| 订单 | 按状态筛选，标记发货、填快递单号，处理取消和退款；预约订单用日历视图 | 立即生效 |
| 顾客 | 顾客名单、消费记录、导出 | 只读 |
| 店铺设置 | 联系方式、营业时间、取消规则、收款配置 | 联系方式和营业时间属于内容修改；收款配置立即生效 |
| 页面 | 跳转到预览和对话改站 | 内容修改 |

库存的扣减规则：下单时预占库存，付款超时（比如 15 分钟）未付自动释放；付款成功后正式扣减。预约时段同理。

### 渲染方式：服务端渲染

店铺页用服务端渲染（SSR）输出完整的 HTML，不做纯前端渲染。原因：

- 搜索引擎和**没装 Skill 的 agent** 直接抓网页时，能读到完整内容
- 微信里打开、手机弱网下，首屏更快

页面里静态的部分（店铺信息、商品、横幅）可以缓存；动态的部分（可预约时段、库存）在页面加载后由前端调接口获取，不缓存。

### 让任意 agent 都能发现这家店

每个店铺站点自动带上三样东西，即使消费者的 agent 没装 OpenShop Skill，打开链接也能知道怎么下单：

- 页面里嵌入 schema.org 的结构化数据（JSON-LD），标注店铺、商品、价格、营业时间
- `/llms.txt`：用文字说明这家店卖什么，以及如何通过 MCP 或 Skill 下单
- `/.well-known/openshop.json`：店铺 ID、MCP 地址、Skill 安装方式

这样问题 7 里"商家分享一个链接给消费者的 agent"就真正成立了：链接本身就是入口。

**实现说明（2026-10-21）：** 现在店铺挂在 `/s/:slug` 路径下，同一个域名上有很多家店，所以 `llms.txt` 和 `openshop.json` 也放在每家店自己的路径下：`/s/:slug/llms.txt`、`/s/:slug/.well-known/openshop.json`。以后改成子域名时，它们会变成域名根目录下的标准位置。

### 域名的三个层级

| 层级 | 地址 | 谁能用 | 技术实现 |
|---|---|---|---|
| 路径 | `openshop.xx/s/nail-studio` | 所有店，默认 | 无额外工作 |
| 子域名 | `nail-studio.openshop.xx` | 所有店 | 泛域名解析加泛域名证书 |
| 自定义域名 | `www.nail-studio.com` | 专业版 | 商家添加 CNAME 记录指向我们，再加一条 TXT 记录证明域名归属；我们按需自动签发证书（比如用 Caddy 的 on-demand TLS） |

### 国内特有的问题：ICP 备案

这是部署方案里最大的约束，**以下是我的理解，具体以云厂商和管局的要求为准**：

- 网站放在中国大陆的服务器上，域名必须先做 ICP 备案，否则云厂商会拦截访问
- **商家的自定义域名**同样要备案，而且要在我们使用的云厂商做"接入备案"。这对小商家门槛很高，周期以周计
- 平台为大量商家提供在线交易，可能还涉及经营性 ICP 许可证（ICP 证）。黑客松阶段影响不大，商业化之前要确认
- 放在香港等境外服务器可以免备案，但大陆访问速度和稳定性差一些，在微信里打开也可能受限

**决定（2026-10-15）：** 我们没有公司或个体户主体，个人备案大概率会因为"经营性内容"被驳回，所以**部署在海外，不做备案**。第一版只做路径和子域名，不做自定义域名。

**补充（2026-10-21）：** 以后也不会有公司或个体户主体，所以**永远部署在海外，不做备案，也不考虑迁回大陆**。扩展方案只在海外机房里做。

### 黑客松阶段的部署

比赛要求评审期间作品已部署、可正常访问，支付宝的异步通知也需要公网地址，所以 12 月 9 日前至少要部署一套：

- **机房选新加坡或东京，不选香港**。商家 agent 要从服务端调用 Claude API，而 Anthropic 不支持在香港和中国大陆使用 API，放在香港会直接调不通。新加坡和东京都在支持范围内，到大陆的延迟也还可以接受
- 一台云服务器（比如阿里云国际站或腾讯云的新加坡节点），上面运行：Caddy（负责 HTTPS 和泛域名证书），一个 Node 服务（API、MCP、店铺渲染、商家工作台），Postgres
- 一个普通的 `.com` 等域名，不需要备案，配置泛解析 `*.openshop.xx`
- 暂时不需要 CDN，等流量上来再加

**海外部署带来的影响和应对：**

| 影响 | 程度 | 应对 |
|---|---|---|
| 大陆访问稍慢 | 小 | 店铺页服务端渲染，页面做轻；图片压缩，以后可以接 CDN |
| **未备案的域名在微信里打开可能被拦截或提示风险** | **大**，商家主要在微信群里分享 | 分享时以二维码和小红书为主；店铺页提供"复制链接到浏览器打开"的提示；消费者通过 agent 下单不受影响 |
| 支付宝接口和付款通知 | 不受影响 | 支付宝开放平台的接口在海外服务器上可以调用，付款通知也能送达。正式接入时再验证一次 |
| 商家的自定义域名 | 不受影响 | 海外部署不需要备案，以后做专业版的自定义域名反而更简单 |

### 部署相关的里程碑调整

- M2 起，店铺渲染用 SSR，并按 `Host` 头或路径识别店铺
