# 开发中自行决定的事项

MVP 阶段，实现细节和小的产品细节由开发时自行决定，记在这里，不逐条确认。需要改的话，直接改代码并更新这里。重要的产品决策仍然记在 [product-decisions.md](product-decisions.md)。

## M2 店铺网页（2026-10-21）

- **网页订单的凭证存在 cookie 里**：HttpOnly，SameSite=Lax，作用路径为 `/s/:slug`，有效期 30 天，HTTPS 下加 Secure。凭证不进网址，也就不会出现在日志和 Referer 里。代价是订单只能在下单时用的那个浏览器里查看。以后如果要跨设备查看，可以给订单页做一个“用手机号查询”的入口
- **快递订单的收货人直接用下单人**的称呼和手机号，表单上不单独填写
- **服务端的报错改写成用户能看懂的话**再显示在表单里。时段被抢走时，页面自动刷新可选时段
- **JSON-LD 的店铺类型**：有营业时间的店标成 `LocalBusiness`，只发快递的店标成 `OnlineStore`
- **发现文件放在每家店自己的路径下**：`/s/:slug/llms.txt`、`/s/:slug/.well-known/openshop.json`。以后改成子域名，它们自然落在标准位置
- **agent 订单不带 `returnUrl`**：付完款停在收银台的成功页，用户回到对话里继续。网页订单付完款跳回订单页

## 产品和架构上自行决定的（2026-10-21）

- **商家登录用支付宝登录**：商家本来就要绑定支付宝收款，登录用同一个账号。开发阶段先保留开店时生成的商家令牌
- **商家工作台按手机优先设计**，做成 PWA，浏览器推送也靠它。不做微信小程序
- **店铺网站有多个页面**：店铺首页加每个商品的详情页，下单在商品页完成
- **黑客松阶段不做跨店目录**：消费者靠商家分享的链接找到店，再加上每家店的 `llms.txt` 和结构化数据
- **演示阶段不限制商家 agent 的 AI 用量**，只记录用量，等做专业版时再定额度
- **里程碑顺序**：M2 → 部署准备 → M4a → M4b → M5。M6 只做最基本的订单处理，M7 不做
- **集成测试和早期试用都由团队自己完成**

## 发布前要改的

- `llms.txt` 和 Skill 里的 `npx -y openshop` 用的是暂定的包名。定了 npm 包名以后两处一起改
- CLI 的默认服务器地址在构建时指定：`OPENSHOP_DEFAULT_SERVER=https://<域名> pnpm --filter @openshop/cli build`。不指定时默认是 `http://localhost:8788`，所以发布到 npm 前一定要带上这个变量构建

## 部署准备（2026-10-21）

- **未付款订单改由后台任务同步**：每个实例每 10 秒（`PAYMENT_SYNC_MS`）尝试做一次同步，向支付方查询所有未付款订单。多个实例时，用数据库里的一张租约表（`leases`）保证同一时刻只有一个实例在同步；实例中途崩溃，租约 60 秒后过期，由别的实例接手。没有用 Postgres 的 advisory lock，因为连接池里加锁和解锁可能落在不同连接上，PGlite 也不好模拟
- **读取时不再整店查询支付方**：
  - 顾客查看或取消自己的订单时，仍然会当场刷新这一单
  - 查库存、查时段、下单前，只结算这家店**已经过期**的未付款订单，这样超时的订单不用等后台同步，也不会继续占着库存
  - 商家发货前会当场刷新这一单，避免刚付款还没同步就被拒绝发货
  - 商家看到的订单列表和顾客名单，最多比实际情况晚一个同步周期（约 10 秒）
- **图片存储接口**：`Storage` 只有 put、url、delete 三个方法。现在用 `LocalDiskStorage`，存在 `UPLOADS_DIR`，由 app 自己在 `/files/...` 提供访问，缓存设为永久，因为文件名是随机的、不会复用。多实例部署时换成阿里云 OSS（用 S3 兼容接口），代码里留了说明
- **上传接口**：`POST /api/merchant/uploads`，请求体直接放图片的原始字节，不用 multipart，方便 agent 和 curl 调用。只收 JPG、PNG、WebP、GIF，上限 5 MB；类型看文件开头的字节，不信任请求头里声明的类型
- **镜像直接用 tsx 运行 TypeScript 源码，不另外构建**：工作区里的包导出的都是 .ts 文件，店铺页面是 .tsx，打包反而麻烦。启动多花大约一秒。镜像里只安装 server 和它依赖的包
- **Postgres 用 17**：18 版改了数据目录的挂载位置，没必要现在踩
- **每日备份**：一个单独的 compose 服务，每天北京时间 3 点用 pg_dump 导出数据库，同时打包上传的图片，保留 14 天，存在服务器的 `deploy/backups`。复制到服务器以外（OSS）的做法写在 `docs/deploy.md`，需要时再配
- **泛域名证书先不配**：店铺现在按路径区分，用不到子域名。泛域名证书要走 DNS 验证，需要带阿里云 DNS 插件（caddy-dns/alidns）的 Caddy，配置写好了，先注释掉
- **数据库迁移编号**：这次加了 `0001_leases`。如果别的分支也生成了 0001，合并时要把其中一个迁移重新生成

## M4a 店铺骨架（2026-10-21）

**店铺状态**
- 店铺分“草稿”和“已上线”。新店（`/api/shops` 和 `/api/onboarding`）都是草稿，第一次发布后上线。草稿店对顾客、网页、公开接口、MCP 和 CLI 一律表现为“找不到店铺”，商家只能通过预览链接看到。数据库迁移把已有的店都设成已上线
- 下线、暂停营业等状态暂时不做

**页面区块**（定义在 `packages/core/src/page.ts`）
- 第一版有 8 种区块：店铺信息（必选，只能有一个）、推广横幅、商品展示、营业时间（只能一个）、相册、图文介绍、联系方式（只能一个）、自定义内容
- “预约”模块不单独做区块：预约服务就是“商品展示”区块按交付方式筛选出来的；“营业时间”区块显示营业时间、取消规则和预约须知
- 推广横幅只能链接到本店商品，不能填任意网址
- 每个区块的参数存成 `{ id, type, v, props }`，`v` 是参数版本。读的时候先按迁移函数升级到当前版本再校验。一页最多 30 个区块
- 新增区块不指定位置时，放在“联系方式”上面
- 主题只有三项：主色（#RRGGBB）、字体（默认、圆体、宋体）、圆角（直角、小圆角、大圆角）。按钮文字颜色按主色深浅自动选黑或白
- 没有页面配置的老店，按 M2 的布局生成默认页面

**自定义内容的安全处理**
- 用 `sanitize-html` 按白名单过滤：只留排版类标签、链接和图片；去掉脚本、事件属性、iframe、表单和 style。链接只允许 http(s)、tel、mailto，并强制新窗口打开、不带 referrer；图片只允许 http(s)
- 写入时过滤一次，渲染时再过滤一次，以防白名单以后收紧
- 商品图片和区块图片只接受 http(s) 链接或站内路径（`/` 开头），一个商品最多 9 张

**行业模板**（`packages/core/src/templates.ts`）
- 6 个行业：美甲美睫、理发造型、私教健身、摄影写真、烘焙零售、其他。每个行业有默认模块、主题、营业时间、取消规则、横幅和图文文案、2 到 3 个示例商品
- 开店时可选的模块：预约、购买、推广横幅、相册、图文介绍。店铺信息和联系方式总是有；勾了预约才有营业时间；示例商品按勾选的预约或购买筛选
- 开店不指定店铺地址时，自动生成 `行业-6位随机`，比如 `nail-3fa9c1`
- 模板内容直接写进草稿店的线上数据，不进待发布修改，所以第一次发布的修改清单里只有商家自己的改动

**示例内容**
- 示例商品带 `sample` 标记，预览里显示“示例”角标
- **有上架的示例商品时不能发布**，返回 `sample_content` 并列出商品名，避免顾客买到假服务。商家修改过的示例商品算真实商品（标记清除），或者直接删除
- 横幅、图文的示例文案不拦截发布，它们不会让顾客下错单

**待发布修改**（`apps/server/src/content.ts`、`studio.ts`）
- 修改就是一条 op，存成数据，M4b 的 agent 工具直接生成同样的 op 调用 `POST /api/merchant/changes`。op 类型：`shop.update`、`theme.update`、`section.add/update/move/remove`、`product.create/update/delete`
- op 在提交时就分配好所有新 id（商品、规格、区块），预览和发布重放时结果一致，商家在预览里看到的商品 id 发布后不变
- 店铺信息、营业时间（每周时段、同时接待人数）、取消规则、页面、主题、商品（包括价格、规格、上下架）都走待发布修改
- 立即生效的经营操作：库存（`PUT /api/merchant/variants/:id/stock`）、临时休息（`PUT /api/merchant/closures`，整体替换列表）、发货、取消退款
- 原来的商品接口 `POST/PUT/DELETE /api/merchant/products` 保留，但改成提交修改：返回发布后的样子加 `change`。DELETE 从 204 改为返回 `{ change }`
- 商品编辑里的库存只作为**新规格的初始库存**；已有规格的库存永远不会被发布覆盖。商品从预约改成快递时，规格库存按编辑里的值设置
- 规格按位置保留 id，和 M1 一样
- 和现有内容完全一样的修改会被拒绝（`no_change`），修改清单里不会出现空操作
- 每条修改附一句给商家看的说明，比如“法式美甲 ¥168→¥188”“主色 粉→红”“新增「推广横幅」：周末 8 折”“把「相册」移到第 1 位”。颜色名按色相粗略判断
- 删除商品时，横幅和商品展示区块里指向它的引用自动去掉
- **撤销**一条修改，会连同之后对同一对象（同一个商品、同一个区块、主题、店铺信息）的修改一起撤销，因为商品修改保存的是完整内容，后面的修改包含了前面的结果；之后因此失效的修改也一起撤销。返回撤销了哪些
- 每家店同时只有一个进行中的修改集，数据库用部分唯一索引保证；所有修改操作都先锁店铺这一行，串行执行

**发布和回滚**
- 发布在一个事务里写入所有变化，记一个版本号，保存发布后完整内容的快照。没有修改又已上线时返回 `nothing_to_publish`；草稿店没有修改也能发布（直接上线），清单记为“店铺上线”
- 回滚到某个版本：把那个版本的快照写回线上，记成一个新版本（“回滚到版本 N”）。有待发布的修改时不允许回滚，要先发布或放弃
- 回滚会恢复之后被删除的商品和规格（只是把软删除标记去掉），库存保持当前值
- 快照里的页面在回滚时会按迁移函数升级到当前区块版本

**预览链接**
- 地址形如 `/s/:slug/preview/<过期时间>.<签名>`，HMAC-SHA256 签名，密钥来自环境变量 `PREVIEW_SECRET`，有效期 24 小时。放在路径里而不是查询参数里，预览页里的链接都留在预览中
- 没设密钥时启动随机生成一个并打印警告，重启后旧链接失效
- 预览页加 `noindex`，顶部有“预览”提示条，不放 llms.txt 和 JSON-LD；预览里的商品页不能下单
- 预览里空的相册、图文和没开预约的营业时间区块显示一行提示，线上直接隐藏

**M2 收尾**
- 订单页用和取消接口相同的规则，**事先**告诉顾客点了会怎样：未付款显示“取消预约/订单”；可退款显示“取消预约并退款 ¥168”；不能取消时不显示按钮，改为显示原因和店铺电话。点击前弹确认框
- 取消用普通表单提交到 `/s/:slug/orders/:id/cancel`（依赖 cookie 的 SameSite=Lax 防跨站），处理完 303 跳回订单页，没有 JS 也能用
- 商品图片：列表里显示 72px 缩略图，网格布局显示方图，商品页顶部横向滑动的图片条；第一张立即加载，其余懒加载，都写了宽高避免页面跳动。没有图片时什么都不显示

**发布前要改的**
- 部署时设置 `PREVIEW_SECRET`
- 本地模拟收银台页面没有 favicon，浏览器会请求一次 `/favicon.ico` 得到 404，换成真实支付后不存在这个问题
